# Vision phase 2: synchronized dual-camera virtual camera

## Intent and status

Replace independent CPU-heavy camera processing and video encodes with synchronized 4K capture, GPU analysis/rendering, one clean H.264 encode shared with the overlay-off live outputs, and a second encode only when live overlay is requested. Raul approved the decisions below on 2026-11-16 for incremental implementation; performance, calibration, and interop remain hardware gates. The legacy pipeline stays the default until integrated HIL acceptance. This document makes no product code, proto, or app changes.

## Existing system and scope

`src/adapters/capture/frame/gstreamer/gstreamer.cpp:85-93,256-374` reads 4K from Argus, VIC-downscales to 1080p **system-memory** NV12, maps each buffer on CPU and timestamps at sample conversion. `src/app/pipeline/services/orchestrator/pipeline-orchestrator.cpp:175-201,209-290` copies source planes into CPU memory, samples two latest-only camera slots without timestamp pairing, CPU-postprocesses, then sends frames to independent record/stream sinks. The stream can be CPU-composited side-by-side (`:294-355`); the recording is already clean. `src/adapters/raw_capture/` writes two 854x480@15 H.264 proxy MP4s; `src/adapters/storage/gstreamer/`, `src/adapters/streaming/gst_rtmp/` and `src/adapters/streaming/gst_rtsp/` each own an x264 encoder. RTSP only starts its encoder on a viewer. The timeline-backed on-demand L2 export already exists in `src/adapters/overlay/burn/` and stays. Current capture IDs are per camera, and `captured_at` is not a camera clock: neither proves synchronization. Existing `calibration.json` has per-camera K and distortion but no relative R; defaults are placeholders (`src/app/config/services/config_loader/config-defaults.hpp:37-43`). The app/BLE surface has manual camera selection, side-by-side preview, independently selectable record/stream modes, and no dedicated live-overlay toggle.

Goals: 1920x1080@30 clean virtual view, both 4K sources retained in device memory until rendered, batch-two RF-DETR analysis at 10–15 Hz, one panorama-space tracker/director, bounded 1–2 s look-ahead, synchronized full-res still pairs, and predictable recording finalization. Non-goals: full-resolution panorama, raw-video proxy, post-match camera re-framing, 4K recording, extra codecs or encoders, real-time L2 export, rewriting networking or the BLE transport. Anti-goals: silent timestamp pairing by dequeue time, unbounded NVMM pinning, CPU-copying 4K frames at video rate, or preserving a preview mode by adding a third x264 encoder.

## Approaches considered

1. **Chosen target: NVMM frame-pair buffer + GPU virtual remap + encoded H.264 distribution.** Best fits no-NVENC encode budget and continuous cross-seam framing; hardest part is verified NVMM-to-CUDA/VPI interop and lifetime/fence handling. A small on-device gate precedes migration of the live output.
2. CPU composite/downscale then share encoded output: easier to wire from current OpenCV pipeline, but retains 4K per-frame host transfer and consumes CPU needed by x264. Reject.
3. GPU-generate a full stitched panorama then crop: simpler director coordinates but doubles high-resolution memory traffic/storage and spends memory needed for the delay ring. Reject.

VPI Remap and CUDA are **implementation alternatives**, not two concurrent renderers. Start with a small measured VPI/NVMM interop trial; if its cross-camera seam or synchronization cannot meet the budget, use a CUDA texture remap directly from each source instead. Do not merge an unverified interop path into the default runtime. Neither API's exact JP7.2 behavior has been verified in this phase.

## Pipeline and ownership contract

A `VideoSurface` is an opaque move/copy-cheap handle to a referenced `GstBuffer`/NVMM allocation (DMA-BUF or validated VPI/CUDA wrapper), format/geometry, capture timestamp, camera index, and release fence. No CPU plane pointer is advertised for a GPU-only frame. GPU consumers wait for producer fences; references persist until the last analysis, delayed-render, or sampler user signals completion. Release returns the surface to the capture pool, never while a kernel or encoder conversion still reads it. Keep hardware handles inside adapters; domain/app ports carry neutral metadata and opaque ownership, not `Gst*`, CUDA or OpenCV types. The existing CPU `Frame` remains only for compatibility at the final 1080p encoder/snapshot boundary; `MaterializeFrame` and CPU `FrameBundle` are removed from the capture hot path.

| Stage, rate | Owner / memory | Handoff and back-pressure |
| --- | --- | --- |
| Argus cam0/cam1, 3840x2160 NV12 @30 | Per-camera GStreamer owns NVMM `GstBuffer`; adapter retains by ref with actual sensor/GStreamer timestamp and fence; no map/copy | Minimal capture callbacks enqueue handles to per-camera bounded synchronizer input (3 each); replace oldest on overload, count drops; serialized Argus restart/health watchdog preserved. |
| Pair synchronizer, @30 | Owns two referenced NVMM surfaces + normalized timestamp and skew | Align by capture time, not dequeue/frame ID. Publish at most one matched pair per output tick to delayed ring and latest-only analysis slot; drop unmatched older input; propagate health/discontinuity. |
| Analysis, 10–15 paired samples/s | VIC produces two small NVMM inputs; TensorRT CUDA buffers own resized/normalized batch=2 tensor; host receives **only boxes/scores/metadata** | One worker processes newest pair; skip stale work rather than queue inference. Fence before reuse; one panorama-space tracker/director consumes results. Use a deterministic synthetic detector first for integration; real RF-DETR requires a separately reviewed model artifact and accuracy gate. |
| Delay ring, nominal 1.5 s | Retains up to 45 *pairs* of full-res NVMM surfaces (bounded additionally by bytes); analysis uses shared refs | FIFO on pair PTS. Release only after render/sampler finishes. At capacity, evict oldest not in flight; if the delay target cannot be maintained, record a discontinuity and hold last camera pose, never allocate without bound. |
| Director + GPU virtual renderer, @30 | One worker reads paired full-res NVMM (VPI/CUDA), generates **one** 1920x1080 NVMM NV12 output; blend only pixels crossing overlap | Pose (yaw/pitch/zoom) chosen from latest eligible tracked observations with timestamps at or before the delayed pair's presentation time + look-ahead window; never use detections from the future beyond available buffered data. Duplicate/late analysis does not stall video. A real seam requires calibrated K, distortion, R, and exposure/color agreement; without validated K/distortion/R, refuse match START on the new pipeline with an explicit "calibration not ready" error to the app. After a valid START, cam1 loss degrades to cam0-only, flags health, and preserves the clean recording. |
| Clean encode | VIC converts output NVMM to system-memory I420 **once** at 1080p30; x264 owns encoded access units in system memory | Bounded leaky pre-encoder queue with drop counters; assign monotonically increasing PTS/DTS and durations from render cadence, not `appsrc do-timestamp` arrival. Keep one encoded clean bus with independent bounded subscribers; record sink may not lose a finalized file because a network branch blocks. |
| MP4, RTMP, RTSP | Recorder `h264parse -> mp4mux` on clean encoded bus; clean live RTMP/RTSP subscribers package same encoded AUs without re-encode | Tee before MP4 mux; parsers/payloader/muxer per sink, own nonblocking queues, request IDR + SPS/PPS on attach, preserve segment timestamps. Stop record: drain encoder/mux and wait EOS for moov, report failure if not finalized; never discard the only clean file to save latency. Network stalls drop that network branch and resync at keyframe; RTSP remains lazily connected and retains current bind/auth behavior. |
| Overlay ON live | Cached Cairo RGBA scene is uploaded/updated on change; GPU composites only 1080p stream view, VIC downloads I420, **one additional** x264; RTSP+RTMP share this overlaid encoded bus | Second encode exists only with at least one overlay-on viewer/stream; overlaid branch never feeds L1. Toggle routes new subscribers at IDR and maintains timestamp continuity; clean encoder remains when recording, otherwise only the requested variant is encoded. |
| Still sampler | Selected pair retained from synchronizer/ring; controlled NVMM-to-host transfer of **only selected 4K pairs**, encoded as still images off capture thread | One pair/30 s while match active; app-triggered BLE burst: 10 synchronized pairs at 2 Hz. Bounded writer queue (2 pairs), write both images and manifest in a temporary pair directory, then atomically rename that directory to a published pair name on the same filesystem; readers ignore temporary directories. On partial failure remove the temporary directory and count failure. Separate match UUID folder; propose a configurable 2 GiB still-pair quota with oldest completed match-pair eviction, never evict active or temporary groups, and surface quota exhaustion as a dropped-sample error. Confirm retained duration on real JPEG sizes before fixing this default. Never expose these files in recording catalog or old proxy download API without a deliberate contract. |
| Snapshot/L2 | Latest rendered 1080p frame can be downloaded to CPU on demand for existing thumbnail/AWB; L2 remains existing offline decode + timeline replay + encode | No continuous CPU snapshot conversion. Record an explicit mapping between overlay event clock and clean L1 media PTS, including skipped frames and pause/resume. Update the existing L2 burner to use decoded media PTS (it currently uses decoded frame index / nominal fps at `src/adapters/overlay/burn/opencv-overlay-burner.cpp:324-329`); no offline burn during live record/stream. |

The clean bus must exist when recording OR an overlay-off RTSP/RTMP subscriber needs it. If no recording and only overlay-on output exists, only the overlaid encode is necessary; creating a redundant clean encoder is not. A clean preview with no recording is one unavoidable lazy encoder; overlay-on preview during clean recording costs the second. With record and stream active, **maximum two** simultaneous x264 encodes independent of viewer count. A separate stream `quality`/fps or a side-by-side preview cannot be achieved from the same H.264 access units; do not silently claim tee sharing while honoring conflicting modes. The approved output contract is fixed 1920x1080@30 for record and all live video; 720p60 and independent quality choices are dropped and incompatible requests receive an explicit error.

## Timing, synchronization and continuity

- Use each camera buffer's sensor-origin capture timestamp (or verified common Argus monotonic reference timestamp), transformed into a **single monotonic timebase**; record raw timestamp, normalization offset, and pair PTS. Independent pipeline running-time PTS or `steady_clock::now()` at `Capture()` return are not valid measures of exposure skew. At HIL, verify both timestamp origins/rates and sensor start phase; without a trustworthy common clock, mark sync unavailable and do not claim synchronized stills or blend a seam.
- Accept nearest-PTS pairs in capture order with configurable max absolute skew **half a frame interval + 2 ms** (about **18.7 ms at 30 fps**); log skew for every pair. Phase 1 measured free-running sensor nearest-PTS skew 14.71–16.92 ms, median 16.51 ms, so 10 ms would reject valid pairs. Hardware sync is being researched separately in phase 1b; tighten the threshold only after measurement. Wait at most **one frame interval (~33 ms)** for the counterpart, then discard the older unmatched frame. Never reuse an old partner as a new pair. A single dropped frame causes one dropped pair and at most one duplicated output view at the renderer's constant cadence; retain last valid pose, mark discontinuity, and never write a falsely paired still. Match START requires both healthy cameras and validated K/distortion/R on the new pipeline; without calibration return "calibration not ready" to the app. During an active session, cam1 loss continues clean cam0-only recording with degraded health and STOP/download usable; if cam0 is also down, existing session failure/stop handling applies. Return to paired mode only after a fresh synced pair and calibrated seam is ready.
- Target **1.5 s** pair buffer, configurable by pair count/bytes (45 pairs at 30 fps). 3840×2160 NV12 ~12.44 MB/surface; 45 pairs use ~1.12 GB of pixel payload plus alignment/pool/analysis/render overhead (budget ~1.3–1.6 GiB NVMM), sharing the Orin Nano's 8 GB with OS and TensorRT. Before fixing 1.5 s as the delay, measure peak total and available memory with a TensorRT engine loaded during capture/ring saturation and a sustained run; require no OOM, allocation failures, or memory growth and sufficient headroom for the loaded engine and renderer. If this gate fails, repeat at **1.0 s / 30 pairs**; if even 1.0 s fails, stop for Raul's decision. At startup warm the buffer before emitting; live stream/RTSP starts with that delay and codec reorder/network add latency. On memory pressure, report underflow and drop old pairs rather than grow; do not secretly switch to full-frame CPU buffering. Still pairs use the same timestamps as the view. Measure drift during 30+ min capture and after Argus restart.
- Director receives both cameras' detections in one batch, undistorts with per-camera K/distortion and rotates rays by calibrated R into a shared spherical/panorama coordinate frame. Gate overlapping detections by spatial/angular + class/time, assign one track ID, then choose a rate-limited yaw/pitch/zoom pose with a central safe framing when no confident track exists. Renderer samples each output ray in the relevant full-res camera; exposure/seam feather only in a small overlap band. Synthetic detections are explicitly nonproduction; only real validated K/distortion/R permit a new-pipeline match START.

## Budget hypotheses and validation (NOT measured on this redesign)

30 fps gives 33.3 ms wall time/tick; 6 cores give 200 core-ms/tick theoretical. GPU/VIC and memory bandwidth are independent bottlenecks. Estimates below are planning envelopes to reject bad designs, not observed tegrastats readings; do not add GPU percentages as if GPU and VIC were one resource.

| Stage | Provisional 30-fps load | Instrument on Jetson in later HIL step |
| --- | --- | --- |
| 2× 4K Argus capture + pair/ring ownership | CPU 5–12 core-ms/tick, ISP/VIC hardware; ~1.3–1.6 GiB ring | Argus/PID thread CPU, NVMM allocation and memory controller, dropped samples, pairing skew p50/p99. |
| VIC downscale / tensor prep @10–15 batch/s | CPU 2–6 core-ms/tick, VIC/GR3D transfer; tensor size depends on model | VIC utilization, CUDA events + batch prep timing, sysmem copies (expect none per full frame). |
| RF-DETR batch=2 + projection/tracker/director | GPU inference **unknown** until engine exists; provisional 5–20 ms per inference and CPU 2–6 core-ms/tick | TensorRT/CUDA events p50/p95/p99, GR3D, batch rate, missed deadlines and track continuity. If >66–100 ms per batch, 10–15 Hz fails. |
| Virtual remap + seam @30 | provisional GPU 3–10 ms/tick, CPU 2–5 core-ms/tick, VIC convert 1–4 ms/tick | GPU kernel/event p95, GR3D/EMC/VIC; check <=33.3 ms combined render critical path under inference load. |
| Clean x264 1080p30 + mux | provisional **1.5–3 CPU cores**, i.e. 50–100 core-ms/tick; strongly preset-dependent | per-encoder CPU, encode p95, input/output frame counts, leaky drops, PTS, MP4 validity after 30+ min and STOP. |
| Additional overlay-on x264 + network | provisional **1–2.5 CPU cores** (33–83 core-ms/tick); highest-risk case | same counters for second encoder while record+RTMP+RTSP+inference run; if ceiling exceeded, do not ship overlay-on as a guaranteed 1080p30 mode. |
| Still pair once/30 s; burst 2 Hz | negligible steady encode average, burst CPU/I/O spike **unknown** | disk write p95, dropped sample pairs, encode CPU spikes, record frame drops during burst. |

Run `tegrastats` at 1 s intervals alongside per-process/thread CPU and instrumented stage timers/counters for >=10 min warm and >=30 min sustained tests: idle, capture-only, clean record+RTSP, record+RTMP+RTSP+batch inference, and same with overlay ON and still burst. Log board clocks/thermal throttling, CPU utilization/frequency, GR3D, VIC, EMC, RAM/NVMM, and frames in/out; compare with baseline at same clocks and sensor mode. Acceptance proposal: 30 rendered frames/s with no sustained queue growth; <=1% dropped rendered/encoded frames (excluding separately counted capture failures); 10–15 completed inference batches/s; p99 valid pair skew <= configurable half-frame + 2 ms (18.7 ms at 30 fps), with every pair's skew logged; no truncated MP4; no second encoder with overlay OFF; memory bounded for 30 min. If two encodes fail, stop and bring measured trade-offs to Raul rather than silently reducing recording fidelity.

## BLE/app migration and compatibility

- Preserve matching/record STOP, pause/resume, session snapshot/finalization, clean L1 filenames/downloads, overlay timeline and L2 export, RTSP endpoint/auth, RTMP destination handling, camera-health gates and emergency controls. Preview is the same virtual broadcast camera at fixed 1920x1080; side-by-side `SetPreviewLayoutCommand` and `SetActiveCameraCommand` are **semantically obsolete**. Keep commands backward-compatible as explicit `ERROR`/unsupported responses with unchanged wire field numbers while app hides `Both` and manual-camera controls; only remove schema fields in a coordinated proto-first release after checking for wire breaks. Never acknowledge side-by-side while returning a single virtual view. Session snapshot must no longer claim a stale side-by-side/manual layout.
- The proxy command/record metadata fields are **already reserved** (`proto/bluetooth.proto:563-569,689-703`); do not reuse them for stills. Replace internal `ProxyOwners` lifecycle with sampler ownership and retention, while keeping historical proxy files untouched. Add the app-triggered calibration-burst BLE command and status (including still pair count/failure) to proto/app/mock in the coordinated contract task; additive fields are wire-compatible but **treat the changed feature contract as breaking for rollout/review**, coordinating firmware/app protocol version and pins. Stop if `buf breaking` identifies a wire break; do not decide its migration alone.
- Add an explicit user live-overlay preference defaulting OFF (wire shape belongs to the coordinated contract task), independent of `PushOverlayLayout` scene visibility. A scene pushed for post-match L2 must not automatically force a live second encode. App setup/session UI, BLE serialization, mock backend and tests must reflect it. The same preference affects RTSP preview and RTMP (not clean L1, not the L2 timeline). RTSP viewer and RTMP must share the same chosen encoded variant when present; no implicit third encode.
- Current separate recording and streaming `VideoQuality` choices (and advertised 720p60 despite 4K sensor at 30 fps) conflict with a fixed common encoded tee. Advertise only 1080p30 while this pipeline is active; reject incompatible mode requests **explicitly** (do not silently create another encoder or misrepresent fps), and align app options/mock/firmware spec. Drop 720p60 and independent quality choices. This is a **behavioral breaking change** even if proto field numbers remain. Decide whether a later lower-resolution mode is worth a separately negotiated single common encode.
- Schema changes, if selected, follow proto `development` PR first, protocol version bump for removals/renames, then merged-commit submodule pins in firmware/app; same feature branch name, green `just ci`, coordinated `feat(scope)!:` titles for real wire breaks. This phase opens no PR and changes no proto.

## Migration gates and deletion

1. Prove common timestamp/NVMM lifetime and interop while existing pipeline stays the default; add ring/pair tests in the cross-compile container and labeled hardware sync/zero-copy tests. No frame copied from full-res NVMM per tick.
2. Add periodic+burst still sampling and verify paired files/retention without touching historical proxies. First merge can be separately shipped with old video pipeline; only switch off proxy producers when new sampler is actually producing valid pairs.
3. Introduce GPU renderer + deterministic director/synthetic detections under an explicit deployment gate, keep default recording untouched until seam calibration and load succeed. Add calibrated projection/dedupe/tracker/inference behind the same gate; move to RF-DETR only after the engine passes batch tests.
4. Move clean recording to the single encoded bus; keep legacy RTSP/RTMP temporarily behind the gate, then route overlay-off stream+preview from the bus. Prove MP4 EOS, IDR attach and network backpressure before removing redundant encoders. Overlay-on second bus only after bounded two-encode load passes.
5. Coordinate proto/app UI and preference changes; switch the default only after HIL proves the integrated budgets. Then remove `src/adapters/raw_capture/filesystem-raw-capture-sink.*`, `proxy-launch.*`, `proxy-retention.*`, old `IRawCaptureSink`/`ProxyOwners` and tests, `IDecision`/`ManualDecision`/`StaticDecision`, CPU `OpenCvSideBySideCompositor`, hot-path `OpenCvPreprocessor`/`OpenCvPostprocessor` and `MaterializeFrame`, and standalone unused `GstOverlayCompositor` **only after** all references and tests are migrated. Keep Cairo scene/timeline, offline `OpenCvOverlayBurner`, clean-recording guard and download exclusions for legacy proxy names. Historical proxy files are not deleted automatically.

Every code merge must build with the cross-compile container `just ci changed` (unit/contract/integration tests; hardware tests written but labeled `hardware`). HIL is required **later** for Argus timestamps, NVMM/VPI/CUDA interop, long-running 30-fps/thermal/encode tests, JPEG burst and real RTSP/RTMP reconnection; this design-only phase uses no Jetson.

## Raul decisions and implementation gates (2026-11-16)

- Fixed 1920x1080@30 for recording and all live outputs; incompatible requests fail explicitly. Live overlay defaults OFF, shared by RTSP preview and RTMP.
- New-pipeline match START requires both cameras healthy and real validated K/distortion/R; return "calibration not ready" otherwise. An active match continues clean cam0-only recording with degraded health if cam1 fails. The old pipeline remains the default until the new path is gated in.
- Sample one paired still every 30 s while active; add an app-triggered BLE burst of 10 pairs at 2 Hz in a coordinated proto/app release. Propose 2 GiB quota pending real image-size/retention evidence.
- Keep `SetPreviewLayoutCommand` side-by-side and `SetActiveCameraCommand` on the wire but answer explicit unsupported errors until coordinated removal.
- Live clock continues through PAUSE; L1 media PTS excludes paused time and L2 skips overlay events during paused spans.
- Use synthetic detections first; RF-DETR requires a separately reviewed artifact and accuracy gate. JP7.2 found but ignored `camera_overrides.isp` in the phase-1d extreme-matrix test; no ISP override ships. Store a calibrated per-camera 3×3 colour matrix and per-channel gain with K/distortion/R, derived from a colour chart or overlapping scene, and match cam0/cam1 colour in the seam/overlap in the GPU renderer. Phase 1b owns `aeantibanding=3` in `src/adapters/capture/frame/gstreamer/gstreamer.cpp`; rebase on `development` before changing that file.
- Stop for Raul if JP7.2 NVMM/VPI/CUDA interop fails, even a 1.0 s measured ring cannot fit, or a proto change is a wire break.

**Research limitation:** Hindsight reads return an MCP output-schema error; this design uses Raul's decisions and the phase-1/phase-2 handoff reports. Context7 VPI docs were quota-limited; VPI/NVMM interop remains an explicit hardware verification gate.
